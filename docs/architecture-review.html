核心洞察:为什么 Embedding 找不到「InnoDB刷盘 → 定时任务批量刷盘」

这不是 embedding 模型不够好,是向量空间组织错了对象。同一个 embedding 技术,换个被 embedding 的对象,就从不灵变灵。

✗ 在「内容空间」里找类比(你现在的设想)

InnoDB Buffer Pool 刷盘redo logMySQL 崩溃恢复
定时任务批量刷盘 ← 向量距离很远TCC → 订单预扣 ← 更远
内容空间按「话题相似」组织:都在讲 MySQL 的近,讲定时任务的远。而类比恰恰发生在话题很远的地方。
结论:embedding 适合召回同话题材料(L2 检索层),不适合做跨域迁移发现(L4)。

✓ 在「机制空间」里找类比(修正后)

机制卡: 内存累积+阈值触发+批量落盘+崩溃可恢复
InnoDB 刷盘 ─analog─ 定时任务批量刷盘 ─analog─ 批量INSERT合并
把每个知识点翻译两次:一次是内容(归 embedding 管),一次是机制(问题形态/解法结构/权衡/适用边界)。L4 的匹配走在机制卡空间。
关键:对机制描述文本做 embedding,类比就近了;LLM 再判定边类型与置信度 —— 正好接上你 L2 想要的「评判标准+置信度机制」。

🔗 is-a / contains(骨架边)

juc → jvm → jmm

你说的"天生关联性"。来自 L3 图谱抽取,树/图结构,人审成本低。

用途:学习路径、前置知识导航、多跳遍历的主干道。

⚡ analog(迁移边)

刷盘思想 ≈ 批量刷盘

跨域机制同构。只能生在机制卡之间,LLM 判定 + 置信度 + 人审队列。

用途:"这个新知识,像我已懂的什么?" —— 快速拆解类比的核心。

🎯 applies-to(应用边)

TCC → 订单预扣/解锁

模式 → 具体业务场景的显式落地。你从业务里反向标注,越用越准。

用途:"这个机制能用在哪" —— 你强调的"对知识有良好的应用"。

Demo 范围砍法(YAGNI):4 周只验证一件事 —— 「新知识能否自动挂到我的机制卡上」
