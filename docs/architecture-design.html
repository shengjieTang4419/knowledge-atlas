Personal Knowledge OS · Architecture

个人知识 OS —— 让新知识挂得上、用得出

搜索感兴趣的知识 → 用自己熟悉的方式拆解类比 → 挂载到已有知识节点 → 在真实场景中灵活应用
产品的全部设计服务于这个飞轮:挂载与应用是目的,搜索与图谱是手段,沉淀反过来让下一次搜索更准。
01

架构分层:四层流水线 + 一个横切服务

数据自上而下流动:理解问题 → 找到材料 → 组织形态 → 建立迁移。Profile 不在流上,而在每一层的组装现场。点击各层查看职责契约。

L1 · Topic 层 Query Understanding

把「一句话兴趣」翻译成「一组可检索的问题」—— 搜索 / 拆解 / 改写 / 关键字
▼ 子查询 + 关键字

L2 · 检索层 Hybrid Retrieval

双通道召回 + 置信度治理 —— 人工策展与机器召回互为兜底
▼ 命中文档 + 候选实体

L3 · 图谱层 Representation

知识的形态:wiki 骨架(实体/关系) + Markdown 血肉(文档跳转)
▼ 实体节点 + 关联问题

L4 · 知识层 Mechanism

知识的迁移:机制卡 + 三种关系,让 juc→jvm→jmm 相连,让刷盘思想流向批量任务

⚡ Profile 服务 Cross-cutting Context

横切注入:L1 的拆解策略 · L3 的呈现形态 · L4 的类比偏好 —— 同一份知识,按你的思维模式输出

02

两条主链路:沉淀与消费

写入链路决定体系的质量上限,查询链路决定体验的下限。两条链路共享同一份索引与机制卡库。

写入链路 · 沉淀

文档进 → 知识挂上体系。机器生成一律过信任闸,人肉确认才入库。
1
文档接入Markdown 真相源入库,git 可版本化、可回溯
2
骨架抽取LLM 抽实体/关系 → edges 表,渲染 wiki 骨架
3
机制卡抽取按固定 schema 抽「问题形态/解法结构/权衡/适用边界」
4
挂载建议机制卡空间召回候选 → LLM 判边型 + 置信度
⚖ 信任闸:置信度 >0.8 自动挂 · 0.5~0.8 进待确认队列 · <0.5 丢弃 —— 人只审中间带
5
入库成网节点 + 边写入,索引重建,进入可被检索的体系

查询链路 · 消费

问题进 → 按你的思维模式输出,并顺手告诉你「它该挂在哪」。
1
Topic 理解拆解 / 改写 / 关键字,一次调用产出子查询组
2
三路召回BM25(精确) + 向量(语义) + 图游走(多跳)
3
重排组装rerank 后按 Profile 切片组装上下文
4
类比生成在机制卡空间找「你已懂的同构机制」,新知挂旧知
5
带引用输出答案 + 骨架跳转 + 挂载建议(它该连到体系的哪个节点)
03

核心数据模型:机制卡 × 三种关系

系统只有一种「一等公民」(机制卡)和三种「关系」。关键修正:类比不是实体之间的边,而是两个实体共享同一张卡涌现出来的。
🃏 机制卡(Mechanism Card)
name机制名称,如「批量阈值落盘」
problem解决什么问题形态(不是解决什么业务)
mechanism核心机制:一句话说清怎么做到的
tradeoff权衡:付出了什么代价
boundary适用边界:什么时候不该用它
cases迁移案例集:已知出现在哪些领域
🔗

is-a / contains 骨架边

实体 ↔ 实体,客观知识层级。LLM 抽得准、量大、稳定,是网的经纬。

juc → jvm → jmm:前置知识链,多跳遍历的主干道。
🎯

applies-to 锚点边

机制卡 ↔ 实体,把抽象拉回具体场景。从真实工作反向标注,越用越准,是网的密度。

TCC 卡 → 订单流水的预扣 / 解锁:知道能用在哪,才叫学会。
⚡

类比 涌现关系 · 不是边

两个实体共同指向同一张卡,「一看就通」自然涌现。少而精、主观、要人审,是网的高度(金线)。

InnoDB 刷盘 & 定时任务批量写:都挂在「攒批写」这张卡上。
04

卡 / 实例两层模型 —— 机制卡的生死线

机制卡模型的成败,不在「能不能抽出卡」,在「卡」与「实例」是不是分成了两层。你的三个例子,恰好是三种关系,各归各的。
你的例子它是什么关系谁管它
juc → jvm → jmm 天生关联is-a / 前置:客观知识层级图谱骨架(实体层内部横向连)
InnoDB 刷盘 → 定时任务批量刷盘同一张卡的两个实例,不是一条边机制卡 + applies-to
TCC → 订单预扣 / 解锁机制 → 业务场景applies-to 锚点边
网体 vs 金线 · 网体 = is-a(骨架) + applies-to(锚点),量大、稳定、LLM 抽得准;机制卡 = 网里的金线,少而精、主观、要人审。你之前把最难最稀缺的 20%(机制卡)当成了网的全部,所以觉得撑不起一张网——反过来,机制卡决定网的高度,不决定网的密度。
05

技术栈:一个文件扛索引,复用优先于新建

Python 全家桶。原则是:已解问题用现成服务,资源全部投给机制层。
部件选型为什么
真相源Markdown + frontmattergit 可版本化;Obsidian 直接可视化;人写零成本。血肉永远是人可读的文本
索引SQLite 单文件:FTS5 + sqlite-vec + edges 表BM25 / 向量 / 图 三个索引进一个文件;demo 期不引入 Neo4j/Milvus/ES
多跳遍历SQLite recursive CTE个人知识量级(万级边)下,递归查询足够;图数据库是规模化之后的事
检索服务复用本地 WeKnora已在跑、有 API;混合检索是已解问题,不重造
LLM / Embedding现有 relay(dashscope / ifans)通道现成;机制卡抽取、改写、判边全走这一路
重排bge-reranker小成本换召回质量,性价比最高的一个组件
信任闸LLM-as-judge + 三档置信度>0.8 自动 / 0.5~0.8 人审 / <0.5 丢弃,人的注意力只花在中间带
Profileprofile.yaml + 组装器注入先手工维护三个开关,验证「注入即生效」;画像学习是后话
06

贯穿全线的设计原则

这些不是口号,是每一层做取舍时的裁决依据。

机制即资产

文档会过时,机制卡不会。系统沉淀的真正资产是机制卡库与边网络,软件只是它的容器。

无非必要,不增实体

每加一个组件先问谁触发它。demo 期索引不配拥有独立中间件,能复用的绝不自建。

信任分级,人肉只审中间带

机器产物全是不可信输入:高置信自动过、低置信自动弃、人的注意力只投给灰色地带。

骨架可糙,血肉必须可信

机器抽的骨架允许不完美(可重抽);入库的血肉(文档/机制卡)必须人写或人审。

挂载优先于收藏

一条新知识入库时必须回答「它连在哪」。连不上的知识,宁可暂存待确认,不做孤岛收藏。

契约先行

层与层之间只认契约(子查询组 / 召回集 / 实体节点 / 机制卡),实现可换,契约不动。
